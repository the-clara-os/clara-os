How to build ClaraOS, start it, and work at its prompt and in its windows.

This manual is for version {{version}}. ClaraOS starts in a virtual machine, tests itself as it comes up, and ends at a prompt where what you type is Common Lisp: it is read, evaluated, and what it gives is printed. There is no shell and there are no commands apart from that. Listing a directory, writing a file and saving the whole system are Lisp forms like any other.

What the manual shows of the prompt was typed at a running kernel: the tests that every change has to pass type each of these sessions again and compare the answers. The front page says what ClaraOS is for and how far it has come.

{{spleen:Getting it}}

ClaraOS is built from its source, on macOS or on Linux. There is nothing to download but the repository, and nothing is installed on your computer: the result is a directory of files, and a disk image made of them, for a virtual machine to start from.

On macOS the tools come from Homebrew:

brew install llvm lld qemu sbcl

On Ubuntu they come from the distribution:

sudo apt install clang lld make qemu-system-x86 qemu-system-arm ovmf \
    qemu-efi-aarch64 netcat-openbsd sbcl python3 dosfstools

Then, on either:

git clone https://github.com/the-clara-os/clara-os
cd clara-os
make               # both kernels, and the Lisp files beside them
make test          # if you like: start every machine and check its answers

make takes a few seconds and leaves everything in build/. Building and running need clang, QEMU and Python 3, which macOS has with Apple's developer tools. SBCL and the rest of the list are for make test.

{{spleen:Starting it}}

Under QEMU

make run-aarch64   # virtualized on Apple silicon: it starts at once
make run-x86_64    # emulated: the firmware takes a few seconds first

A window opens, which is the machine's screen, and the terminal you started it from becomes its serial port. Both show the same report as the machine comes up, and both end at the prompt. You can type in either: in the window on the machine's keyboard, in the terminal on its serial port.

(clara.system:shut-down)at the prompt: the machine saves its world and turns itself off, and QEMU ends. Stopping it has the other ways.
Ctrl-A Xin the terminal: leave QEMU, whatever the machine is doing, which is the plug pulled
Ctrl-A Cin the terminal: QEMU's own monitor, and back
MEM=1G make run-aarch64a machine with that much memory, where it has 512 MiB otherwise
WORK=~/clara-work.img make run-aarch64a machine with a second disk, one of your own
NET= make run-aarch64a machine without a network card, where it has one otherwise

The machine starts from a disk image, build/disk-aarch64.img or build/disk-x86_64.img, which is made of the files in build/esp the first time and kept from then on. Files that you write are on it the next time, and so is a world that you saved. A newer build does not make the disk again: make run-aarch64 hands the machine the build as a second disk, the system that is running takes it and starts the machine again, and the newer system comes up with your files where they were. A newer ClaraOS says what happens there.

FRESH=1 make run-aarch64a new disk for the machine, as if it had never run. The one that was there is kept as build/disk-aarch64-before.img.

In UTM

  1. make image, on macOS. It makes build/claraos.img, a disk with both kernels on it.
  2. In UTM: New, then Virtualize on Apple silicon (the machine is AArch64) or Emulate (x86_64), operating system Other. Skip the ISO. Leave "UEFI Boot" checked. 512 MiB of memory is plenty.
  3. Remove the drive that UTM made. Then Drives, Import, build/claraos.img, with the interface VirtIO: that is the disk ClaraOS has a driver for. With any other interface the machine still starts, and has no files.
  4. Add a Serial device, mode "Built-in Terminal". The system talks there as well as on the screen, and you can type there.
  5. For typing in the screen's own window, add a keyboard that ClaraOS has a driver for. UTM gives a machine USB devices, which it does not have one for. Under QEMU, Arguments, add two: -device virtio-keyboard-pci and -device virtio-tablet-pci. The second is the pointer, which the window manager is worked with.
  6. To fetch by HTTPS, the machine needs a device that makes random numbers. When the system's report says random: no device that makes numbers which nobody can guess, add one more argument there: -device virtio-rng-pci.
  7. Start.

UTM copies the disk into the virtual machine, and that copy is the machine's from then on. To put a newer ClaraOS on it, give the machine the newer build/claraos.img as a second drive and tell the system to take it: A newer ClaraOS. To go back to a system that nothing was written on, import build/claraos.img again in place of the drive; the files that were written on the old drive go with it, and so does a world that was saved there.

What it needs of a machine

A processorx86_64 or AArch64. One is used, however many the machine has.
FirmwareUEFI. The kernel is the program that the firmware starts: there is no boot loader between them.
Memory128 MiB is enough to start and to work. It is given 512 MiB unless you say otherwise.
A diskA virtio disk with a FAT volume, of 12, 16 or 32 bits, behind either kind of table of partitions or without one, that the firmware can write to. The volume it starts from is the one whose files it sees, until it is told to look on another disk's.
A place to typeA serial port, a virtio keyboard, or both.
A screenThe one the firmware sets up, if there is one. Without it everything is on the serial port.
A pointerA virtio mouse or tablet, for the window manager. Nothing else has a use for one.
A network cardA virtio network card, for fetching files and a newer ClaraOS. A machine without one starts and works all the same.

It has no use yet for sound, for USB or for a clock.

Stopping it

The machine is shut down by asking it to:

> (clara.system:shut-down)
clara: the world is saved
clara: turning the machine off

It saves the world, so that the next start goes on where this one left off, stops the applications, has the disk keep what was written to it, and turns the machine off: the window closes, and QEMU ends. (clara.system:start-again) does the same and then starts the machine again at once, in the world that it saved. There are three ways of asking:

At a prompt(clara.system:shut-down) and (clara.system:start-again). With :save nil the world is not saved, and the next start is in the one that was saved last, or in a new one when none was.
In the window managerShut Down and Restart, at the end of the list under Applications.
By the power buttonwhich is how a host asks a machine to stop: system_powerdown in QEMU's monitor, and Request power down in UTM. The system looks at the button four times a second.

A machine that is asked to shut down asks its windows first. An editor whose text is not saved holds it back: its window comes to the top, the machine stays on, and the answer says why.

> (clara.system:shut-down)
error: the machine is not shut down: the window "/notes.txt" has text that is not saved. Finish that, or ask with :FORCE T, which goes on without

Save the text or close the window, and ask again; (clara.system:shut-down :force t) does not ask. Asked by the power button or from the list, the machine says the same on the serial port and stays on. What else goes with the machine is whatever a thread was in the middle of: a file that a program had open for writing and had not closed is not written.

Ctrl-D at the first prompt ends the session without any of this. The kernel says clara: nothing more to do, halting and the machine stands still, deaf to its power button, until the host stops it. Stopping a machine from outside, with Ctrl-A X or by closing its window, is the plug pulled. Files are safe then, since a file is on the disk from the moment the form that wrote it has answered; what the world has become since it was last saved is gone.

{{spleen:The prompt}}

The prompt is > and a space. What you type after it is a form of Common Lisp. When the line holds a whole form, the form is evaluated and its value is printed, in the way it would have to be typed to mean the same thing. Then the prompt comes back.

> (+ 1 2)
3
> (list 1 "two" 'three #\4)
(1 "two" THREE #\4)
> (floor 17 5)
3
2
> (values)
> 'one "two" (+ 1 2)
ONE
"two"
3
> (list 1 2
        3)
(1 2 3)

A form that gives several values has each of them on a line of its own, and one that gives none has nothing. Several forms on a line are answered one after the other. A form that is not finished when the line ends goes on in the next line, after a prompt of two spaces, for as many lines as it takes.

Keys

Enterends the line
Backspace, Deletetakes back the last character of the line
Taba space
Ctrl-Cwhile you type: gives up the line, and the form it was part of. While a form is evaluated: stops it.
Ctrl-Dat the start of a line: ends the session, and the machine halts

That is all the editing there is. The arrow keys do nothing, and no line that was typed before can be called back. In a terminal on the serial port, the terminal's own copy and paste do what is missing: many forms can be pasted at once.

The keyboard is read as one of the United States, with Shift, Ctrl and Caps Lock, and a key that is held down repeats. What is typed on the serial port can be any character, as UTF-8. The screen shows the characters of ASCII, and a box for any other.

A Listener window has the same keys, with one difference: there Ctrl-D closes the window, and the machine goes on.

The screen holds 100 columns and 37 rows at 800 by 600 pixels, and what scrolls off its top is gone. The terminal on the serial port keeps whatever a terminal keeps.

Mistakes

A mistake costs a line. The system says what went wrong, in words, and the prompt comes back with everything as it was.

> (car 5)
error: CAR wants a list, and 5 is not one
> (no-such-function 1 2)
error: the function NO-SUCH-FUNCTION is not defined
> (loop)
Ctrl-C
error: interrupted from the keyboard

A form that does not end, like that (loop), runs until Ctrl-C stops it. So does one that waits for something that never comes.

{{spleen:The language}}

The Lisp is a part of Common Lisp, and not a dialect of its own: what is here means what it means in any Common Lisp, and a program that keeps to this part runs elsewhere as it stands. If you know Common Lisp, read where it stops short and go on. If you do not, any introduction to it will do, for as far as this part goes.

What you type is compiled before it runs, by a compiler that is written in this Lisp like the rest of the system, and what the compiler makes is written out once more as the instructions of the machine's own processor, which then runs it with nothing in between. The system runs the same way: its console, disks, file system and windows are written in this Lisp.

Functions, macros and variables

> (defun fact (n) (if (< n 2) 1 (* n (fact (- n 1)))))

A function takes its arguments in the ways Common Lisp has: required ones, &optional ones with their defaults, the rest as a list, and by keyword. A macro can take a list apart in its own list of parameters. A variable that defvar or defparameter made is special: binding it with let changes what every function sees until the let is over, as *depth* shows above.

Errors that a program handles

> (handler-case (/ 10 0) (division-by-zero () 'no-quotient))
NO-QUOTIENT

> (unwind-protect (car 5) (format t "cleaning up~%"))

> (defun forever (n) (+ 1 (forever n)))

An error is a condition, with a type. handler-case takes the conditions whose type one of its clauses names, and unwind-protect cleans up whichever way its form is left. The system's own errors have Common Lisp's types where a program would want to tell them apart: type-error, division-by-zero, unbound-variable, undefined-function and their kin. A stack or a heap that is full, and Ctrl-C, are no errors: ignore-errors and a clause for error let them pass, and a clause for serious-condition takes them.

Where it stops short

What is refused is refused with an error that says so. Nothing is quietly taken for something else, so a program does not mean one thing here and another elsewhere.

  • Numbers are integers of 63 bits. No larger integers, no ratios, no floating point.
  • loop is the plain one, a body that is repeated until a return. Its keywords, for and collect and the rest, are not there. do, dolist and dotimes are.
  • format knows ~A, ~S, ~D, ~% and ~~.
  • The functions on sequences, mapcar, find, remove-if, sort and the others, take lists. length, subseq and concatenate take strings as well. Of their keyword arguments there is :test, with :key for member, assoc and sort, and :initial-value for reduce.
  • make-string takes :initial-element and not :element-type: there is one kind of character, and one kind of string.
  • defstruct takes a name and slots, and none of its options.
  • Conditions are handled by handler-case. There is no handler-bind, no restart and no debugger.
  • There are no hash tables, no classes and generic functions, and no typep.
  • A package can be made, used when it is made, exported from, and deleted when no other uses it. Nothing is imported or shadowed afterwards.
  • eq and eql are the same function. Letters change case as far as ASCII has them: (string-upcase "é") is "é".
  • A function can call itself some six thousand calls deep. Past that it is the error above, and not the end of the machine.
  • (declare (special ...)) and &environment are refused, and so are the reader's #., #S and #P.

{{spleen:The compiler}}

Whatever you define is compiled. The compiler goes through a function once and writes down what an interpreter would have to find out again at every call: where each variable is, which form is a call and which a loop, what every macro stands for. What it leaves is a list of small steps, instructions, which are translated for the machine's processor in turn, and the processor runs the function. That happens when a form is typed at the prompt, when a file is loaded and when eval is given a form, so there is nothing to ask for:

> (compiled-function-p #'fact)
T
> (compiled-function-p (lambda (n) (* n n)))
T
> (funcall (compile nil '(lambda (n) (* n n))) 12)
144

The system is compiled in the same way. The console, the file system, the window manager, the applications and the compiler itself are Lisp, and when a machine starts from the Lisp files the compiler first compiles itself, what translates for the processor then translates the compiler and itself, and everything after that is compiled and translated as it is loaded. That takes half a second, or some ten seconds where the machine is emulated. A world that is saved holds all of it compiled, and a machine that starts from one does none of that work again.

compile is still there: (compile nil '(lambda ...)) gives the compiled function of a form, as above, and (compile 'fact) leaves a function that is compiled already as it is.

How quick

time evaluates a form and says how long that took, to a hundredth of a second, which is how often the system's clock ticks. On one machine:

> (defun fib (n) (if (< n 2) n (+ (fib (- n 1)) (fib (- n 2)))))
FIB
> (time (fib 30))
10 milliseconds
832040

The interpreter that ClaraOS had before it had a compiler, which walked the text of fib at every call, took 390 milliseconds for the same on that machine, and the compiler's instructions took 70 when the kernel carried them out, before they were translated for the processor.

What it made of a function

disassemble writes the instructions of a function out, with their numbers:

> (disassemble 'fact)
FACT: 1 local variable, 4 words of stack, translated for the processor
0   LOCAL 0
1   CONST 2
2   <
3   JUMP-IF-NIL 6
4   CONST 1
5   RETURN-ONE
6   LOCAL 0
7   CONST FACT
8   LOCAL 0
9   CONST 1
10  -
11  CALL 1
12  *
13  RETURN
NIL

The instructions work on a stack. LOCAL puts the value of a variable on it, which is known by its number: n is variable 0. CONST puts a constant there. < takes two numbers off the stack and leaves T or NIL, so the first three are (< n 2), and JUMP-IF-NIL 6 goes on at instruction 6 when that gave NIL. CALL 1 takes an argument off the stack and the function under it, calls it, and leaves what it gives. The rest is (* n (fact (- n 1))).

A function is found by its name at the moment it is called: define fact again, and compiled code calls the new one. The commonest functions of the kernel have an instruction each, which does the work without a call: car, cdr, not, null, consp, atom, 1+ and 1- of one argument, and cons, eq, +, -, *, <, >, <=, >=, =, aref and svref of two. Such an instruction looks first whether its name still means the kernel's function. If you have defined * again, it calls yours.

Given a lambda form, disassemble shows what compiling it makes. A function that is part of the kernel has no listing.

For the processor itself

The instructions that the compiler leaves are for a machine that the kernel plays: it takes them one at a time, and finds out for each what it asks for. A function is not run that way. ClaraOS makes of those instructions the instructions of the processor itself, AArch64's or x86-64's, which the processor carries out with nothing in between, and it does so for whatever is compiled: what you define, and the system, from mapcar to the compiler.

> (list (clara.native:translated-p 'fact) (clara.native:translated-p 'mapcar))
(T T)

clara.native:translated-p says whether the processor runs a function, or the function of a name. A translated function means what it meant: its mistakes are reported in the same words, and it is found by its name at every call. disassemble lists the compiler's instructions, since those are what the processor's were made of, and says translated for the processor on the first line.

The kernel's machine is still there, and runs what is compiled while clara.native:*translate* is NIL. Functions of the two kinds call each other freely. clara.native:translate takes such a function, or the name of one, and has the processor run it from then on, with every function that was made of it before; clara.native:translate-all does the same for every function that there is, and says how many the processor runs that it did not run before.

> (setq clara.native:*translate* nil)
NIL
> (defun square (n) (* n n))
SQUARE
> (setq clara.native:*translate* t)
T
> (list (clara.native:translated-p 'square) (square 12))
(NIL 144)
> (clara.native:translate 'square)
SQUARE
> (list (clara.native:translated-p 'square) (square 12))
(T 144)
> (clara.native:translate-all)
0

The variable counts at the moment a form is compiled. Set it at the prompt, as above, or bind it around a compile or a load: (let ((clara.native:*translate* nil)) (load "/mine.lisp")). A let around a defun that is typed changes nothing, because the whole form is compiled, and translated, before the let has bound anything.

How much quicker the processor is depends on what a function does. On one machine, with fib compiled for the kernel's machine first:

> (time (fib 35))
750 milliseconds
9227465
> (clara.native:translate 'fib)
FIB
> (time (fib 35))
70 milliseconds
9227465

What gains most is what the processor does alone: the calls from one function to another, the variables and the jumps, and adding, subtracting and comparing small numbers. Fifty million additions in a loop take 610 milliseconds on the kernel's machine and 70 on the processor. What makes lists gains least, because a cons has to be made either way: a million items pushed, reversed and mapped over take 60 milliseconds there and 50 here.

  • The processor's instructions take about four times the memory of the compiler's, and a function keeps both: the listing is of the compiler's, and the kernel's machine does an instruction for the processor when it gets something that it does not usually get, a number too large or a car of what is no list.
  • A function whose instructions for the processor would be longer than a megabyte is left to the kernel's machine on AArch64, where a jump of the processor's reaches no further. clara.native:translated-p says NIL for it, and nothing else tells.
  • They are part of the world that is saved, and come back with it.

What to keep in mind

  • A macro runs when a call of it is expanded, and for a compiled function that happened once, when the function was compiled. Define a macro again, and the functions that were compiled with the old one go on as they were until they are defined again. Macros are compiled like functions.
  • The macros of a macrolet run while the forms around them are compiled, so they cannot use the variables of the function that they are written in. They can use the macros of a macrolet around them.
  • defvar has to come before the functions that bind the variable. That is the order a file has them in anyway.
  • A form that is not what it should be, (if) for one, does not stop the compiler. The compiled function fails when it comes to that form.
  • The kernel still has its interpreter. It runs the first two Lisp files when a machine starts from them, until the compiler has compiled itself, and at every such start the kernel holds what compiled code does against it: some four hundred small programs have to give the same answers both ways.

Compiled functions are part of the world that is saved. (clara.compiler:evaluate form) is the function that eval calls: the form is compiled, and then run.

{{spleen:Files}}

The system reads and writes the files of the disk it started from. The name of a file is a string: the directories that lead to it and then its own name, with a slash before each, as in "/EFI/BOOT/BOOTX64.EFI". Letters match in either case. There is no current directory: every name starts at the top of the volume.

directory takes a pattern, in which * stands for any characters in the last part of the name, and gives the names that fit, a directory's with a slash at its end. probe-file gives the name of a file as the disk spells it, or NIL when there is none.

A disk has three directories once the machine has started from it. /EFI/BOOT holds the two kernels, where the firmware looks for the one to start. /home is yours, and is where the system keeps what you define as text. /clara is the system's own: it holds a directory for the system that runs, named after it, and in time the world that was saved. A system's name is its version and eight digits that are different for every build, so the names of its files are asked for and not spelt out:

> (clara.system:system)
"{{version}}-8f3a1c2e"
> (clara.system:system-file "boot.lisp")

Those are the system's Lisp files: the language's part that is written in Lisp, the compiler, the console, the drivers, the file system, the window manager and what sees to the machine as a whole, and two that are not loaded until they are wanted, the applications editor.lisp and files.lisp. native.lisp is what translates for the processor, with a file for each kind of processor, arm64.lisp and x86-64.lisp, of which a machine loads its own. Beside them are a second copy of the kernels and manifest, the list of what the system is made of, which is what another machine reads when it takes this system from this disk. Everything outside /clara and /EFI is yours, and no system writes there but for one file in /home.

Reading and loading

> (with-open-file (in (clara.system:system-file "listener.lisp")) (list (read-line in) (read-line in)))

with-open-file opens a file for the forms inside it and closes it afterwards. read-line gives the next line, and at the end of the file it is an error, or the value you name: (read-line in nil 'done). load evaluates the forms of a file one after the other, as if they had been typed. When a form in it fails, the error says the file and the line.

What to know about files as they are now:

  • A file is text, in UTF-8. It is read whole when it is opened and written whole when it is closed, so it has to fit in memory, which a text does.
  • A name can be 255 characters long and have spaces in it. It cannot have any of " * : < > ? \ | in it, or end in a dot or a space.
  • A file goes into a directory that is there. (clara.fat:make-directory "/letters") makes one, and (clara.fat:remove-directory "/letters") takes one away that has nothing in it. A file cannot be renamed or moved.
  • There is no clock in the system, so every file it writes is dated the first of January 1980.
  • The disk is a FAT volume, which other systems read. On macOS, build/claraos.img opens with a double click, and the files that ClaraOS wrote are in it.

A disk of your own

The disk that the machine starts from is the system's, and your files are on it beside the system. A machine can have a second disk that is yours alone: nothing here ever makes it again, nothing is written to it that you did not write, and it can be given to another machine, or to a new disk of the system's. Make one once, a FAT volume with nothing on it, somewhere outside build:

mkdir -p build/empty && python3 tools/mkdisk.py build/empty ~/clara-work.img

Then name it when you start the machine:

WORK=~/clara-work.img make run-aarch64

With export WORK=~/clara-work.img in your shell's profile, every make run-aarch64 has it. The report shows two disks then, each with a volume, and says where names are looked up:

disk: 00:02.0 has 72081 sectors of 512 bytes, 35 MiB
disk: 00:06.0 has 72081 sectors of 512 bytes, 35 MiB
files: a FAT32 volume of 33 MiB on the disk 00:02.0, from its sector 2048 on
files: a FAT32 volume of 33 MiB on the disk 00:06.0, from its sector 2048 on
files: names are looked up on the first of these volumes

The first is the system's, so nothing has changed for the files so far. (clara.fat:volumes) gives the volumes in that order, and clara.fat:*volume* holds the one that names are looked up on. Bind it to yours around a form, and the files of that form are the ones on your disk:

> (length (clara.fat:volumes))
2
> (defun work () (second (clara.fat:volumes)))

> (let ((clara.fat:*volume* (work)))
    (with-open-file (out "/mine.lisp" :direction :output)
      (format out "(defun mine () ~S)~%" "kept on a disk of my own")))

> (let ((clara.fat:*volume* (work))) (load "/mine.lisp"))

"kept on a disk of my own"

A file is carried from one volume to the other by reading it with the variable bound one way and writing it with the variable bound the other way. clara.fat:file-text gives the text of a file as one string:

> (defun copy-text (name from to)
    (let ((text (let ((clara.fat:*volume* from)) (clara.fat:file-text name))))

> (let ((clara.fat:*volume* (work))) (directory "/*"))

A let reaches the forms inside it and nothing else. To work on your disk for a while, set the variable instead: then every name is looked up there, in every thread, so the Editor and the file browser open and save there as well.

> (progn (setq clara.fat:*volume* (work)) (directory "/*"))
("/hello.lisp" "/mine.lisp")
> (list (clara:save-image) (probe-file "/clara/clara.image"))

Two things do not follow the variable, as the form in the middle shows for the first. The world is saved on the disk that the machine was started from, since that is where a machine looks for one, and what you define is written down there as well. The applications start either way: the system finds its own files where it started from.

The next time the machine starts, your disk is as you left it, whatever became of the system's in the meantime. A world that was made anew, by a newer system for one, has what you defined at a prompt, and not what a file of this disk defined. One line brings that back, at a prompt or in /home/init.lisp:

> (let ((clara.fat:*volume* (second (clara.fat:volumes)))) (load "/mine.lisp"))
T
> (mine)
"kept on a disk of my own"

A file of yours that loads all the others makes that the only line to type in a new world. What to know about such a disk:

  • The volumes are found anew at every start, so ask (clara.fat:volumes) for yours each time, as work does. A volume that a variable has kept since before the machine was started again, in a world that was saved, is refused.
  • The host opens the disk as well: on macOS with a double click, like the system's. That is the way to carry files in and out, and the whole disk is one file, which is easy to keep a copy of.
  • The host and the machine must not have it at the same time, since each would write without knowing of the other. On macOS, make run-aarch64 ejects a disk that is still open in the Finder before it starts the machine, and says so in the terminal; when something on the Mac is still using the disk, it says that and starts nothing. The other way round nothing stops you, so stop the machine before you open the disk on the host.
  • Any FAT volume will do, as large as you like, made with whatever the host has for that. A disk image that macOS made is one, a .dmg as well, as long as it is a plain read/write image and not a compressed or a sparse one: WORK=~/clara-work.dmg make run-aarch64. The one above has 33 MiB, which is room for a great many texts.

{{spleen:Saving the world}}

Everything that you define lives in the machine's memory, and is gone when the machine stops, unless you save it. clara:save-image writes the whole Lisp world to one file on the disk, as it is at that moment. (What you define at a prompt is also written down as text, as you go, which is what a world is made of again when the saved one cannot be used.)

> (clara:save-image)
"/clara/clara.image"

The next time the machine starts, it finds that file and takes it for its world, in place of loading the Lisp files. The report says so:

lisp: the heap is an image: 2470 KiB that ClaraOS {{version}} saved, from clara.image on the boot volume
lisp: and with it 781 KiB of code for the processor

The second line is what the world's functions are for the processor, which is saved with them. And at the prompt, what was defined is defined:

> (list (fact 10) (compiled-function-p #'fact) (clara.native:translated-p 'fact))
(3628800 T T)
> (hello)
hello from a file
NIL
> (list (depth) (point-x (make-point :x 1)) (unless-zero 2 'two))
(0 1 TWO)
> (probe-file "/clara/clara.image")
"/clara/clara.image"

What comes back, and what does not

  • Functions, macros, structures, packages and conditions that were defined, and the values of variables, come back. So does the package that names were being read in. All of it is compiled and translated for the processor, and comes back as it was.
  • A special variable comes back with the value it has outside every let, also when it was saved from inside one.
  • Threads do not come back. The world starts again at the prompt, and does not go on in the middle of what it was doing. A thread that was running is one that has been stopped, and a lock that was held is free.
  • The window manager is running again when it was running, with one Listener window. The windows that were open do not come back.
  • The devices are found again, as at every start. A world can be saved on one machine and started on another that has other devices, or another screen, as long as it is the same kind of processor.
  • Files are on the disk either way, and have nothing to do with the image.
  • What you defined after the world was saved, on a machine that was then stopped without a shutdown, is not in the image. It is in the text, and the start loads it from there.

Saving again writes a new image in place of the old one. A world of this size takes a fraction of a second to save. Shutting the machine down saves it as well, unless it is told not to.

Going back to the files

> (delete-file "/clara/clara.image")
T

Without the image, the next start loads the Lisp files again, and the world is as new. A disk that nothing was saved on does the same, and has none of your files either: under QEMU, FRESH=1 make run-aarch64; in UTM, import build/claraos.img again.

A world that does not come to its prompt

One thing a world cannot be saved from is itself. A world in which something essential was redefined, and which was then saved, starts like that every time. When such a world does not get as far as its prompt, stop the machine and start it again. Every start is counted on the disk before anything else is done, and the count is taken away when the prompt is reached; a start that finds the count of the one before it still there passes the saved world over and makes a new one from the Lisp files. The report says so:

lisp: clara.image is passed over: the start before this one did not come to its prompt
...
world: the world that was saved did not come to its prompt at the start before this one.
world:   It is kept, and the next start tries it once more; this world is of the files and of /home/

The world that is made in its place has what you defined, from the text. The saved one is kept that first time, since one start that went wrong may have been anything, a machine that was switched off as it started. When the same saved world does not come to its prompt a second time, the world that was made takes its place on the disk:

world: the world that was saved did not come to its prompt a second time: this one takes its place
world: it is saved as it is now, and the next start is in it; (clara.system:report) says this again

And when the start after a world was passed over does not come to its prompt either, the text may be the reason, and the third start has neither: A file of your own.

A world that is broken and comes to its prompt all the same is yours to delete: Going back to the files.

{{spleen:What you define, kept as text}}

A saved world is quick to start and is only good for the system that saved it. So the system keeps your work a second way, as text, which every ClaraOS reads: in /home, on the disk that the machine started from. Two files there are what a world is made of beside the system's own.

/home/defined.lispis written by the system: every form that defines something, as you typed it at a prompt.
/home/init.lispis yours to write: whatever a new world should begin with.

Whenever a world is made anew, from the Lisp files and not from an image, the two are loaded into it, init.lisp first: after an upgrade, after the image was deleted, and when an image was passed over. A world that comes back from its image takes what is new of them: the forms that it does not have yet, which is what was defined after it was saved, on a machine that then stopped without saving, and what you wrote into a file since. A form that the world has is not evaluated a second time.

What is written down

> (defun area (width height) (* width height))
AREA
> (defun area (width height)
    ;; of a rectangle
    (* width height))

> (probe-file "/home/defined.lisp")

The file has the second area, comment and all, where the first one stood:

;;;; What was defined at the prompt, as it was typed. ClaraOS writes a form
;;;; here when it has been evaluated, in the place of an earlier one that
;;;; defined the same name, and loads this file into a world that is made
;;;; anew, after init.lisp. It is yours to read and to change.

...

(defun area (width height)
  ;; of a rectangle
  (* width height))
  • A form is written down when it was typed at a prompt, in any listener, on the serial port or in a window; when it stands by itself, and not inside a progn or a let; when it went well; and when its first word says that it defines something. That is a word of the language's own, defun, defmacro, defvar, defparameter, defstruct, defpackage, define-condition; a macro of yours whose name begins with def; and anything whose name begins with define-, as clara.windows:define-application, and with it clara.windows:install-application. Any other call of a function is not written down, whatever the function is called. A load is, since what a file defined is in none of the forms that were typed, unless it is one of the two files of /home that is loaded.
  • A form that defines a name again takes the place of the form that defined it before, so the file has every definition once, in the order in which each was first made.
  • Forms that were read in another package than the ones before them have a line (cl:in-package "NAME") before them.
  • What is not a definition is not written down. A variable that was changed after its defvar is in the file with the value that the defvar gives it, and a world that is made of the text alone has that one; an upgrade carries the value that it had come to as well. What a defvar did to get its value, it does again. And what Ctrl-E evaluated in the editor is in the editor's file, and not here.
  • Nothing else that takes a definition back is written down: after (delete-package "PLAY") the forms that made the package, and what was defined in it, are still in the file. The file is text, and yours: read it, and take out of it what you no longer want, in the editor. What the system cannot read of it any more it leaves as it is, and goes on after it.

A file of your own

/home/init.lisp is not there until you write it. Whatever should happen in every new world goes into it: loading your own files, starting the window manager, anything that is not a definition typed at a prompt.

> (with-open-file (out "/home/init.lisp" :direction :output)
    (write-line "(defvar *motto* \"a world made anew, and mine\")" out))
"(defvar *motto* \"a world made anew, and mine\")"
> (list (clara.system:home) (clara.system:home-file "init.lisp"))
("/home/" "/home/init.lisp")

When a world is made, the report says what was loaded, and what was not:

home: /home/init.lisp is loaded, 1 form
home: /home/defined.lisp is loaded, 34 forms of it, and 1 was passed over:
home:   (defvar *window* (clara.windows:open-window "A picture" 200 120 :x 500 :y 400))
home:     there is no window manager to open a window with: (clara.windows:start) starts it
  • Each form is evaluated by itself. One that fails is passed over, with its beginning and the reason in the report, and the rest goes on: a form that a newer system no longer understands does not keep a world from being made.
  • A file gets a minute. One that has not come to its end by then is stopped where it is, and the machine goes on to its prompt. clara.system:*patience* is that time, in milliseconds.
  • A load of /home/init.lisp or /home/defined.lisp that stands in one of the two is passed over like a form that fails: the file would load itself without end. A file of yours anywhere else is loaded from init.lisp like from a prompt, with its name looked up on the disk that the machine started from.
  • After two starts in a row that did not come to a prompt, nothing of /home is loaded, in case that is the reason: the world is then the system's alone, the report says so, and the files are there to be put right. (clara.system:load-home) loads the two files into the world that it is typed in, the way a start does, and that world takes what is new of them from then on.

{{spleen:The network}}

A machine with a network card can fetch a file from another machine, open a connection to one, and take the connections that other machines open to it. The card is a VirtIO network card, which a machine under make run-* has unless it is told otherwise, and which UTM gives a machine by itself.

> (clara.net:station)
"52:54:00:12:34:56"
> (clara.net:address)
net: this machine is 10.0.2.15 on its network, 10.0.2.2 is the way out, 10.0.2.3 knows names
net: by IPv6 it is fec0::5054:ff:fe12:3456, fe80::2 is the way out, fec0::3 knows names
"10.0.2.15"

station is the card's own address on the wire, which it has from the start. The machine's address on the network is another matter: it asks the network for one (DHCP) the first time that something wants the network, and says what it was told. A machine that fetches nothing sends nothing. The second line is its address of the other kind, IPv6, on a network that has a router for it.

Under QEMU the network is one that QEMU makes up for the machine. The machine is 10.0.2.15 on it; 10.0.2.2 is the computer that QEMU runs on; and whatever that computer reaches, the machine reaches through it.

The address is the machine's for a time, which the network says with it, a day under QEMU. When half of that is over the machine asks whether it may keep the address, without being told to and without a word, so a machine that runs for a week is still on its network.

Is a machine there

> (< (clara.net:ping "10.0.2.2") 1000)
T

clara.net:ping asks a machine, by its name or its address, to send back what it is sent, and gives the milliseconds that the answer took, as far as the machine's clock tells them apart, which is to a hundredth of a second: 0 for a machine that is near. One that does not answer is asked again every second, and after ten seconds it is an error. The machine answers such a question itself: ping 10.0.2.15 from another machine on its network is answered.

Machines on the way say when they cannot hand a packet on, and the machine listens: a connection to a machine that cannot be reached ends at once with ... says that ... cannot be reached, and not after ten seconds of waiting.

Fetching a file

To have something to fetch, start a web server on the computer that QEMU runs on, in a directory with a file hello.txt in it: python3 -m http.server 8000. Then, on the machine:

> (clara.net:fetch-text "http://10.0.2.2:8000/hello.txt")
"hello from the other side
"
> (clara.net:resolve "claraos.org")
"185.199.108.153"
  • clara.net:fetch-text gives a file that is a text, as a string. An address is http:// or https://, the machine's name or its address, a port when it is not 80, or 443 for https://, and the file's name there. An address of IPv6 stands between brackets: http://[fec0::2]:8000/hello.txt.
  • clara.net:fetch gives any file, as memory: three values, the address of page frames that hold it, how many bytes it is, and how many page frames those are, which are yours to give back with clara.unsafe:free-memory. :limit says how many bytes are taken at most, 16 MiB when nothing is said, and 1 MiB for a text.
  • clara.net:resolve gives the address of a name, as the network's name servers have it: when the network named several, the next is asked when one cannot say or says nothing. What they say of a name is remembered for as long as the answer says that it holds. clara.net:*name-server* names another one to ask, by its address, and clara.net:*name-port* the port to ask it at.
  • What is fetched from an address that begins with http:// comes as the other side sends it, and anybody on the way can read it and change it. That is good enough for a web server on your own computer, and for little else: HTTPS is the other way.
  • A web server may say that a file is to be had at another address, and the machine asks there, three times at most. It goes from http:// to https://, as most web servers send it, and never the other way.
  • The other side has ten seconds to say something, clara.net:*patience* in milliseconds, and what has no answer is asked again every second, clara.net:*again*. clara.net:up brings the machine onto the network without fetching anything.

HTTPS

An address that begins with https:// is fetched over a connection that is kept closed: nobody on the way can read what goes over it or change it, and the machine at the other end has shown that it is the one that was asked for. That is TLS, version 1.3.

> (length (clara.net:fetch-text "https://claraos.org/"))
tls: this system trusts 118 certificates to say who a machine is
30027

The other side shows who it is with a certificate, which somebody signed who has a certificate too, and so on up to one that the system trusts. The machine looks at all of that before it asks for anything:

  • The certificate has to be for the name that was asked for, or for a name with a star that covers it: *.example.org is www.example.org, and not example.org.
  • It has to be good today, and so has every certificate above it. Today is what the machine's clock says, (get-universal-time).
  • The chain has to end in a certificate that the system trusts. Those are the ones of the authorities that sign for the web: the list that Mozilla keeps for its browser, as curl publishes it, in the file roots.pem of the system's directory. It is read the first time that something is fetched this way, which is when the line above is said. (clara.tls:roots) gives their names.
  • The other side has to sign the greeting with the key of its certificate, and both sides end the greeting with a word that only somebody who has heard the same greeting can make.

When one of these is not so, nothing is asked for and nothing is fetched, and the error says which it was.

(clara.tls:trust "/root.pem") adds the certificates of a file to the ones that the system trusts, and says whom they are for; the file is as such files are written, with -----BEGIN CERTIFICATE----- before each. The text of such a file, as a string, does as well as its name. That is for a server of your own, whose certificate no authority signed. A world that is saved keeps what was added; a world that is made again, after an upgrade, does not, so a line in /home/init.lisp is where it belongs.

Two things have to be there, and under make run-* both are:

  • A device that makes numbers which nobody can guess: the keys of a connection are made of them. It is a VirtIO device, -device virtio-rng-pci under QEMU, and RNG= gives a machine without one. IPv6

An address of IPv6 is eight numbers in base sixteen with colons between them, and two colons where zeroes are left out. A machine has two of them on a network whose router speaks IPv6: one that it makes for itself, which begins with fe80 and goes no further than its own network, and one on the network that the router names. It asks the routers when something first wants the network, as it asks for its other address, and both kinds are the machine's from then on.

> (clara.net:addresses)
("10.0.2.15" "fec0::5054:ff:fe12:3456" "fe80::5054:ff:fe12:3456")
> (< (clara.net:ping "fec0::2") 1000)
T
  • Everything in this chapter goes over either kind: ping, fetch, connect and serve take such an address where they take the other, and a port that takes connections takes them by both.
  • A name can have addresses of both kinds, and the machine asks for the kinds that it has itself. It goes by IPv6 first when its own address of that kind is one of the Internet's, which begin with 2 or 3, and by IPv4 first otherwise; when nothing takes the connection at the first address, the next is tried. clara.net:resolve gives the one that comes first.
  • Under QEMU the machine's addresses of IPv6 are on the network that QEMU makes up: fec0::2 is the computer that QEMU runs on, and what lies beyond is reached by IPv6 only when that computer has IPv6 itself. So a machine there goes by IPv4 where it can, as it always did.
  • (setq clara.net:*ipv6* nil), before anything has wanted the network, and the machine does not speak IPv6 at all.
  • On a network where nothing hands out addresses of IPv4 and a router speaks IPv6, the machine says so and gets by with what the router gave it.

What is not there: the machine does not ask whether another machine has made the same address; the second half of its addresses is its card's address, wherever it is; it takes its addresses from the routers' word alone, and not from a DHCP server for IPv6; and packets that were taken apart on the way are dropped.

... is not on this machine's network, and no router has said that it is a way outThe same, for a machine that has an address and no way out.

this machine does not speak IPv6, and ... is an address of itclara.net:*ipv6* was NIL when the machine came onto the network.

A machine that listens

The machine takes the connections that other machines open to one of its ports, once it is told to, and hands each to a function of yours, in a thread of its own. The function is given a stream. read-line gives what the other side says, a line at a time, and NIL when the other side is done; what is written to the stream goes to the other side. When the function returns, the connection is over.

> (defun shout (stream)
    (loop
      (let ((line (read-line stream nil)))
        (unless line (return))
        (write-line (string-upcase line) stream))))
SHOUT
> (clara.net:serve 7 'shout)
7
> (clara.net:with-connection (stream "127.0.0.1" 7)
    (write-line "is anybody there" stream)
    (write-line "and again" stream)
    (list (read-line stream) (read-line stream)))
("IS ANYBODY THERE" "AND AGAIN")
> (clara.net:stop-serving 7)
T
  • clara.net:serve takes a port and a function, or the name of one, which lets you define the function anew while connections are taken. :most says how many connections are taken at once, eight when nothing is said; a machine that asks for one more is told that there is none. Nothing is taken at any port that serve was not told.
  • (clara.net:serving) lists the ports, each as (port taken open trouble): how many connections were taken there, how many of them are open, and what the function last ended in when that was an error, which is not printed anywhere else. clara.net:stop-serving ends it for a port, and the connections that are open with it.
  • clara.net:connect opens a connection to a port of another machine, by its name or its address, and gives the same kind of stream, which is yours to close. clara.net:with-connection does that for you, whichever way its body is left.
  • A line ends with a newline, and a carriage return before it, which the Internet's protocols have there, is no part of the line. Text is UTF-8. What the other side says last without ending the line is a line too. A line of more than 64 KiB is an error.
  • read-line waits as long as clara.net:*patience* says, ten seconds, and then it is an error, which ends a function that does not handle it, and with it the connection. A function that is to wait longer for somebody at a keyboard binds the variable: (let ((clara.net:*patience* 600000)) ...).
  • 127.0.0.1 is the machine itself, to itself, and so is its own address: nothing goes onto the network for either, which is how a function is tried before another machine is there.
  • A world that is saved while it takes connections takes them again when it is started, and says so. A world that is made again, after an upgrade, does not: a line in /home/init.lisp is where serve belongs then.

Under QEMU, the network that QEMU makes up lets nothing in. FORWARD=8007:7 make run-aarch64 has QEMU hand on what connects to the port 8007 of your computer, from that computer only, to the port 7 of the machine: nc 127.0.0.1 8007 there, and what you type comes back in capitals. In UTM the machine is on a network that it shares with the Mac, and is reached at its own address.

Nothing keeps such a connection closed: what a function says and hears there is in the open, for anybody on the way to read and to change. The TLS of this system is the half that asks, for fetching. That is why there is no web server here.

... takes no connection at its port ...Nothing listens there, or as many connections are open there as it takes.

... sent a line that is no text: it is not UTF-8The other side speaks in bytes that are no text, which a stream here cannot read.
... has given the connection upThe other side ended the connection in the middle of something, which a program at the other end does when it is stopped.

{{spleen:A newer ClaraOS}}

A system is one build of ClaraOS: its two kernels and its Lisp files. On a disk it is a directory, /clara and then its name, with a list in it of what it is made of. A newer ClaraOS is another such directory, and the system that is running puts it on its own disk, beside itself: that is an upgrade. The files that you wrote stay where they are, and nothing else on the disk is touched.

Under QEMU

There is nothing to do. When the build is another system than the one on the machine's disk, make run-aarch64 says so and gives the machine the build as a second disk, marked as one to take at once:

tools/run.sh: build/disk-aarch64.img holds ClaraOS 0.0.25-8f3a1c2e, and the build is {{version}}-41d0c97b: the machine is given the build
    as a second disk, takes it, and starts again by itself to try it.

The machine starts as the system that it was, takes the newer one, starts again, and comes to its prompt as the newer one, a few seconds later than usual. Its report tells the story as it goes, in the lines that begin with system:.

In UTM, or on any machine

  1. make image makes the newer build/claraos.img.
  2. Stop the machine. Give it that image as a second drive, with the interface VirtIO, after the drive that it starts from.
  3. Start it, and say: 
    > (clara.system:upgrade)
system: {{version}}-41d0c97b is on the disk, and is tried at the next start
clara: the world is saved
clara: starting the machine again
  4. When the newer system has come to its prompt, the second drive has done its work, and can be taken out again the next time the machine is stopped.

(clara.system:upgrade :start-again nil) takes the system and leaves the machine running; the newer system is tried whenever the machine is next started. :from names the volume to take it from, one of (clara.fat:volumes), where the first disk that holds another system is taken otherwise. From a disk it need not be a newer one: any ClaraOS that is not the one that runs is taken, an older one as well.

Over the network

A newer ClaraOS can also be fetched. The newest one is published at https://claraos.org/releases/: a directory on the website that holds a system as a disk does, and beside the list of its files a signature of that list. When no other disk of the machine holds a system, (clara.system:upgrade) looks there, and says so before it does:

> (clara.system:upgrade)
system: no other disk of this machine holds another ClaraOS, so the newest one is looked for at https://claraos.org/releases/
system: {{version}}-41d0c97b is published at https://claraos.org/releases/, and signed with the key that this system has: its files are fetched
system: {{version}}-41d0c97b is on the disk, and is tried at the next start
clara: the world is saved
clara: starting the machine again

From there on it is the upgrade from a disk: the newer system is tried at the next start, and the old one is there until the new one has come to its prompt. A machine that has the newest ClaraOS already is told so, and has fetched one line.

  • The machine asks there when it is told to, and at no other time. (clara.system:newest) asks which system is the newest that is published, and fetches nothing else.
  • What is published there is the system of the newest commit on the main branch of ClaraOS's repository: it is built and signed there each time a change is merged, and takes the place of the one before.
  • A disk goes first: when another disk of the machine holds a system, that one is taken and nothing is asked of the network.
  • It is fetched by HTTPS, and from no address that begins otherwise: nobody on the way reads what the machine fetches, or tells it that an older release is the newest.
  • And nothing is believed for having arrived. The list of the system's files is held against its signature, with the public half of the key that the release was signed with, which the system has in clara.system:*release-key*; and every file is held against the list, by its length and its SHA-512. What fails either is not taken, and the machine starts as it did before. So a release is its publisher's whatever web server hands it out.
  • Only a newer system is taken: one whose version is higher than that of the system that runs. :any t takes whatever is published there, an older one as well.
  • The system has the place in clara.system:*releases* and the key in clara.system:*release-key*. Another place is named with :from: (clara.system:upgrade :from "https://...") takes the newest system that is published at that address, when it is signed with the key that the system has, and (clara.system:newest "https://...") says which one that is.

To publish a system yourself: make a key, once, and lay the system out as a release, on the computer that builds it.

python3 tools/release.py key my.key          # once: the secret half goes into my.key, the public half is printed
make
python3 tools/release.py make build/esp/clara/{{version}}-41d0c97b releases my.key

Then put the directory releases where a web server hands it out by HTTPS. With a web server whose certificate an authority signed, that is all, and on the machine, with the 64 digits that the first line printed:

> (setq clara.system:*release-key* "8c33f9eb730e625013b19d5ea0646d3dd45fa3a03e5977912319a1cee6529fbe")
> (clara.system:upgrade :from "https://example.org/releases/")

A system that is to look at your place by itself has the address and those digits where lisp/system.lisp defines the two variables, before it is built. make release KEY=my.key RELEASES=releases then lays the release out, and refuses a key whose public half is not the one in that file.

To try it from your own computer, which no authority signs for, the build has a web server and makes the certificates for it:

python3 tools/certs.py certs releases.test    # a root of your own, and a certificate for that name
python3 tools/serve.py releases ports certs   # the file "ports" gets two numbers: a port for names, and the one for HTTPS

The machine has to know the name and to trust the root. Put certs/root.pem on a disk of your own, and with the two numbers, here 8053 and 8443:

> (setq clara.net:*name-server* "10.0.2.2" clara.net:*name-port* 8053)
> (let ((clara.fat:*volume* (second (clara.fat:volumes)))) (clara.tls:trust "/root.pem"))
> (clara.system:upgrade :from "https://releases.test:8443/")

Whoever has my.key can publish a ClaraOS that every machine with that public half takes for the real one. It belongs to nobody but the one who publishes.

An error about a certificateSee HTTPS.

What happens at the next start

The newer system is tried before it takes the old one's place. The firmware still starts the old kernel, which sees that a system is waiting, and starts that system's kernel in place of itself, once. The report of that start begins like any other and ends like this:

system: this is ClaraOS {{version}}-41d0c97b, on trial: the system before it is still in place
system: {{version}}-41d0c97b has come to its prompt, and is the system of this machine from here on

With the second line the newer system has put its kernels where the firmware looks for them and taken the old system's directory away. Until then the old system is whole, and is what the machine starts as: when the newer one stops on the way, with a report that begins with panic:, or stands still, stop the machine and start it again. It comes up as it was before the upgrade, in the world that was saved then, and says:

system: {{version}}-41d0c97b was tried and did not come to its prompt: this is still 0.0.25-8f3a1c2e

A system that failed like that is not taken a second time by itself, however often make run-aarch64 offers it; (clara.system:upgrade) tries it again when you ask. An upgrade that is cut short while the files are still being copied changes nothing: the machine starts as the old system, and the upgrade can be asked for again.

What comes across

  • Every file that you wrote, wherever it is on the disk. The upgrade writes into /clara and /EFI and nowhere else.
  • What you defined at a prompt, as text: the newer system loads /home/init.lisp and /home/defined.lisp into the world that it makes.
  • What your variables had come to, as far as that is text: numbers, characters, strings, symbols, and lists of those. The old system writes those values down as it leaves, and the new one gives them to the variables once the text has defined them.
  • The window manager: it is started when it was running, with one Listener window, and a form of your text that opens a window opens it.
  • Not the world itself. A world belongs to the system that saved it, so the newer system makes one of its own files, and saves it without being asked: the next start is in it. What is no text is not in it: a function that no form of the text defines, a thread, a lock, a list that leads back into itself. A variable that held such a thing has what its form makes anew.

The newer system says which is which as it starts, by name:

world: made anew by ClaraOS {{version}}-41d0c97b, of its files and of what /home/ holds as text
home: /home/defined.lisp is loaded, 35 forms
world: 3 variables have the values that they had come to in the world before:
world:   *ASKED*, *JOBS*, *THREADS*
world: 8 variables held what is no text, and are as their forms make them here:
world:   *ADD*, *BELL*, *CANVAS*, *HELD*, *SEEN*, *SVREF*, *WAITER*, *WINDOW*
world: 3 names that the world before had are not defined in this one:
world:   *SPINNER* (a variable), HI, NOT-WRITTEN-DOWN
world: it is saved as it is now, and the next start is in it; (clara.system:report) says this again

The last of the three lists is what did not come across: names that the old world had, in COMMON-LISP-USER and in the packages that you made, and that nothing in the text defines. They were defined inside another form, by a file that was loaded from inside one, or in the editor. (clara.system:report) says all of it again, at any later time, with every name, where the report of a start says the first few lines of a long list.

The disk needs room for two systems while the newer one is tried, some four mebibytes beside what is there. When it has less, the upgrade says so and does nothing.

{{spleen:Threads}}

A thread is a function that runs beside the others. The prompt is one thread, the listener, and each keyboard and pointer has one. The names are those that Bordeaux Threads made usual, in the package CLARA.

> (clara:current-thread)
#<THREAD "listener">
> (clara:join-thread (clara:make-thread (lambda () (* 6 7)) :name "worker"))
42
> (defvar *jobs* 0)
*JOBS*
> (let ((lock (clara:make-lock)))
    (mapc #'clara:join-thread
          (mapcar (lambda (n) (clara:make-thread (lambda () (clara:with-lock-held (lock) (incf *jobs* n)))))
                  '(1 2 3)))
    *jobs*)
6
> (let ((bell (clara:make-event "bell")))
    (clara:make-thread (lambda () (sleep 1) (clara:signal-event bell)))
    (clara:wait-event bell))
T
> (clara:join-thread (clara:make-thread (lambda () (car 5)) :name "faulty"))
error in #<THREAD "faulty">: CAR wants a list, and 5 is not one
error: the thread #<THREAD "faulty"> ended with an error: CAR wants a list, and 5 is not one
> (defvar *spinner* (clara:make-thread (lambda () (do () (nil))) :name "spinner"))
*SPINNER*
> (clara:thread-alive-p *spinner*)
T
> (clara:destroy-thread *spinner*)
T
> (clara:join-thread *spinner*)
error: the thread #<THREAD "spinner"> was stopped
  • clara:make-thread starts a function of no arguments in a thread of its own, and clara:join-thread waits for it and gives what the function gave.
  • A thread that ends with an error says so on the console, and the error is what join-thread then reports. The other threads go on.
  • A lock is held by one thread at a time. clara:with-lock-held takes it for the forms inside and gives it back whichever way they end.
  • An event counts how often it was signalled. clara:wait-event waits until it has been, and takes one off the count. With a number of milliseconds as its second argument it waits no longer than that, and gives NIL when the time ran out.
  • (sleep 2) waits two seconds. The other threads run meanwhile.
  • clara:destroy-thread tells a thread to stop, which it does at its next step, cleaning up on its way out.
  • clara:interrupt-thread is Ctrl-C for one thread: what it computes, or waits for, ends with the condition clara:keyboard-interrupt, which the thread can handle. A Listener window does this to its own thread when Ctrl-C is typed in it.

The threads take turns, a hundredth of a second each. One of them at a time is evaluating, on the one processor that the system uses, so threads keep the machine answering while something waits, and do not make a computation faster. Each thread has its own bindings of the special variables: one that it binds with let is bound for it alone. A thread costs about a mebibyte and a half of memory.

{{spleen:Drawing}}

Pictures are drawn on surfaces. A surface is a rectangle of pixels in memory. The screen is one, and a program makes others, draws on them out of sight, and shows them on the screen when they are whole. The functions are in the package CLARA.DRAW. A place is counted in pixels from the upper left corner of a surface, first across and then down, and that corner is 0 and 0.

> (defvar *paper* (clara.draw:allocate-surface 160 80))
*PAPER*
> (defvar *ink* (clara.draw:color 232 227 244))
*INK*
> (defvar *red* (clara.draw:color 255 85 85))
*RED*
> (clara.draw:fill-rectangle *paper* 0 0 160 80 (clara.draw:color 30 27 46))
T
> (clara.draw:fill-rectangle *paper* 20 20 40 30 *red*)
T
> (clara.draw:draw-rectangle *paper* 10 10 140 60 *ink*)
T
> (clara.draw:draw-text *paper* 72 28 "Hello" *ink*)
T
> (clara.draw:show *paper* 600 40)
T

The last of these puts the picture on the screen, its corner 600 pixels across and 40 down. Until then nothing of it could be seen.

  • clara.draw:allocate-surface makes a surface of so many pixels across and down, all of them black. clara.draw:surface-width and clara.draw:surface-height say how large one is.
  • clara.draw:color makes a colour of its red, its green and its blue, each from 0 to 255. What it gives is a pixel as this machine's screen has them, a number, and that is what everything that draws takes.
  • clara.draw:fill-rectangle takes a surface, the place of the rectangle's upper left corner, its width and its height, and a colour. clara.draw:draw-rectangle takes the same and draws the outline only, a pixel thick. A line along a row or a column is a rectangle that is one pixel high or wide.
  • clara.draw:draw-text draws a string in the console's font, in which every character is 8 pixels wide and 16 high, with the upper left corner of the first one at the place given. With one more colour after the first, the cells of the characters are filled with it, and without it only the characters themselves are drawn, over what was there. clara.draw:text-width says how wide a string will be.

What lies outside

Nothing is drawn outside a surface, and it is no mistake to try: a rectangle that lies half outside is drawn half. Each function that draws gives T when it drew something and NIL when all of it lay outside. clara.draw:with-clip keeps the drawing of the forms inside it to a part of the surface.

> (clara.draw:fill-rectangle *paper* 150 70 100 100 *red*)
T
> (clara.draw:fill-rectangle *paper* 200 0 10 10 *red*)
NIL
> (clara.draw:with-clip (*paper* 0 0 96 80)
    (clara.draw:draw-text *paper* 72 48 "cut off" *red*))
T
> (list (= (clara.draw:pixel *paper* 30 30) *red*)
        (clara.draw:pixel *paper* 100 56) (clara.draw:pixel *paper* 160 0))
(T 1973038 NIL)

Of "cut off" the first three characters were drawn, up to the pixel 96 across. clara.draw:pixel gives the pixel at a place, or NIL when the surface has none there.

Showing what has changed

A surface remembers which parts of it were drawn on, as a few rectangles: its damage. clara.draw:show copies those parts to the screen and forgets them, so what goes to the screen is what has changed since the last time, however much or little that is. Here it is the three characters and the corner that were drawn since the picture was first shown.

> (clara.draw:damage *paper*)
((72 48 24 16) (150 70 10 10))
> (clara.draw:show *paper* 600 40)
T
> (clara.draw:show *paper* 600 40)
NIL
> (clara.draw:copy-rectangle *paper* 20 20 40 30 *paper* 110 44)
T
> (defvar *arrow*
    (vector #b1000000 #b1100000 #b1110000 #b1111000
            #b1111100 #b1100000 #b0010000))
*ARROW*
> (clara.draw:draw-bitmap *paper* 4 2 *arrow* 7 *ink*)
T
> (clara.draw:damage *paper*)
((4 2 7 7) (110 44 40 30))
> (clara.draw:show *paper* 600 40)
T
  • A rectangle of damage is a list: how far across and down it begins, how wide it is and how high. clara.draw:take-damage gives the same list and leaves the surface without any, and clara.draw:add-damage counts a part as drawn on, to have it shown again.
  • clara.draw:copy-rectangle copies a part of one surface to a place on another, or on the same one: the surface it comes from, the corner of the part, its width and height, then the surface it goes to and the corner there.
  • clara.draw:draw-bitmap draws a picture of one bit to the pixel. The picture is a vector of its rows from the top, each a number whose bits are the pixels of the row, and after it comes how many pixels wide it is. Where a bit is 1 the pixel takes the colour. With one more colour after it, the pixels whose bit is 0 take that; without, they stay as they were.
  • (clara.draw:screen) is the screen as a surface, or NIL on a machine without one. Whatever is drawn on it shows at once, and it keeps no damage.

The console writes on the same screen. A picture that is shown there lies over the text, the lines that are written after it go over the picture where they meet it, and when the text moves up a line the picture moves up with it. So a picture stays where it was put only as long as nothing is printed. A picture that is to stay belongs in a window, and while the window manager runs the screen is its own: what is shown there directly is painted over the next time a window moves.

Memory

A surface takes four bytes for every pixel, 1875 KiB for one as large as a screen of 800 by 600, and that memory is not the heap's: nothing gives it back when the surface is no longer used. clara.draw:free-surface does, and after it the surface cannot be drawn on.

> (clara.draw:free-surface *paper*)
NIL
> (clara.draw:draw-text *paper* 0 0 "gone" *red*)
error: this surface was freed

A world that is saved keeps its surfaces and not their pixels. After the machine has started again, a surface from before is refused with this surface is of a machine that was switched off: make a new one, and draw the picture again. A function that draws it comes back with the world.

There is one font, in one size. There are no lines but those along a row or a column, no circles, and no colours that let what is under them show through.

{{spleen:Windows}}

The window manager puts windows on the screen: each is a surface that a program draws on, in a frame with its title. It takes the screen from the console, which goes on with the serial port, where the prompt stays as it was.

("Listener")

The screen now shows a bar along its top, with Applications at its left-hand end and the system's name and version at the right; a window named Listener, with a prompt in it; and the pointer. It is worked like this:

A click on a windowbrings it to the top. The window on top has the focus: its frame is lit, and what is typed goes to it.
The title of a windowis where to take hold of it: press the button there, move, and let go.
The x at the end of the titlecloses the window, and ends the program in it.
Applicationslists the applications there are, and under a line Restart and Shut Down. A click on a name starts the application, or does to the machine what the name says, and a click anywhere else puts the list away.
Alt and Tabbrings the lowest window to the top, and so each window in its turn.

A Listener window is a prompt like the first one, with the same keys, except that Ctrl-D closes the window and Ctrl-C stops what that window is evaluating. Every listener is in the one world: what is defined in a window is defined at the serial port and in the next window. Each has a thread of its own, so one can compute while you type in another, and each is in a package of its own choosing.

It needs a keyboard and a pointer that the system has drivers for. make run-aarch64 gives the machine both; in UTM they are the two devices that are added by hand. With a keyboard alone, the Listener window still takes what is typed, and the functions below do what the pointer would.

A window of your own

The functions are in the package CLARA.WINDOWS. A window's inside is a surface, and is drawn on like any other. What was drawn reaches the screen with clara.windows:show, as far as the window can be seen behind the others.

> (defvar *window* (clara.windows:open-window "A window of my own" 240 120))
*WINDOW*
> (defvar *inside* (clara.windows:window-surface *window*))
*INSIDE*
> (clara.draw:fill-rectangle *inside* 20 20 80 60 *red*)
T
> (clara.draw:draw-text *inside* 112 44 "Hello" *ink*)
T
> (clara.windows:show *window*)
T
> (clara.windows:move-window *window* 400 300)

300
> (clara.windows:launch "Listener")

> (mapcar #'clara.windows:window-title (clara.windows:windows))
("Listener" "A window of my own" "Listener")
> (clara.windows:window-title (clara.windows:raise-window *window*))
"A window of my own"
  • clara.windows:open-window takes a title and the width and height of the inside, in pixels, and gives the window, on top of the others and the colour of the console's paper. With :x and :y it goes where they say, and otherwise a step down and across from the one before. A window is 24 pixels wide or more.
  • clara.windows:window-surface is what to draw on, and clara.windows:show puts on the screen what was drawn since the last time. It gives NIL when there was nothing.
  • clara.windows:move-window moves a window so that the corner of its inside is at a place on the screen, and gives the place it came to, which is clara.windows:window-position from then on: a window stays below the bar, and never leaves the screen altogether.
  • clara.windows:windows lists the windows from the top one down, clara.windows:focused-window is the first of them, and clara.windows:raise-window brings one to the top.
  • clara.windows:close-window takes a window off the screen and gives its memory back.

A window belongs to the thread that opened it. That thread draws on it, shows it and closes it, and close-window from any other thread is an error for as long as the first one lives. Three functions can be given when a window is opened, for what happens to it meanwhile:

> (defvar *typed* nil)
*TYPED*
> (defvar *keys* (clara.windows:open-window "Keys" 160 40 :key (lambda (code) (push (code-char code) *typed*))))
*KEYS*
> (clara.windows:key-typed 97)
97
> *typed*
(#\a)
> (list (clara.windows:close-window *keys*) (clara.windows:close-window *window*))
(NIL NIL)
  • :key is called with the code of every character that is typed while the window has the focus. clara.windows:key-typed is what the keyboard's driver calls; here it stands in for a key.
  • :pointer is called when a button of the pointer goes down or comes up on the inside of the window, with the place, counted from the corner of the inside, and the buttons that are down: 1 for the left one, 2 for the right, 4 for the middle. clara.windows:pointer-moved is what the drivers of mice and tablets call, with a place on the screen and the buttons.
  • :close is called when the x in the title is clicked, and a window that was given none has no x. It is for the function to see that the window is closed, by the thread that opened it.

The three are called in the thread of the keyboard or of the mouse, not in the window's own. They should note what they were told, or signal an event, and leave the drawing to the thread that the window belongs to.

A fourth, :unfinished, is for a program that holds something which would be lost if its window went: a function that gives a few words about it, such as "text that is not saved", or NIL when there is nothing. The machine asks every window before it shuts down, and does not while one answers in words. (clara.windows:unfinished) gives the windows that do at the moment, each with its words.

A window that is opened with :events t does that by itself: it keeps what happens to it, and its program asks for the next thing when it is ready for it, in its own thread, where it can draw.

> (equal (clara.windows:next-event *heard*) (list :key clara.input:+up+))
T

NIL
> (clara.windows:rename-window *heard* "Heard it")

> (clara.windows:close-window *heard*)

  • clara.windows:next-event gives what happened next, and waits when nothing has: for as long as it takes, or for so many milliseconds, after which it gives NIL. (:key 97) is a key, (:pointer 12 30 1) a button that went down or came up, with the place on the inside and the buttons, and (:close) a click on the x, which such a window always has.
  • A key is the code of the character it types. The keys that type none have codes too, past the last that a character can have, which is char-code-limit: clara.input:+up+, +down+, +left+, +right+, +home+, +end+, +page-up+, +page-down+, +insert+, and +f1+ for the first of the twelve function keys, with the others after it. Escape is 27, Delete 127, and a key that is typed with Alt held has clara.input:+alt+ added to its code.
  • clara.windows:rename-window gives a window another title.

An application

An application is a name and a function. clara.windows:launch calls the function in a thread of its own and comes back with that thread once the application has its window. When the function is done, or its thread is stopped, the windows that the thread opened are closed for it.

> (clara.windows:define-application "Hello"
    (lambda ()
      (let ((terminal (clara.terminal:open-terminal "Hello" :columns 30 :rows 4)))
        (format (clara.terminal:terminal-stream terminal) "hello from an application~%")
        (sleep 2))))
"Hello"
> (clara.windows:applications)
("Listener" "Editor" "Files" "Hello")
> (clara:join-thread (clara.windows:launch "Hello"))
NIL

The window is there for two seconds, and goes with its application. From now on Hello is in the list under Applications, below the three that come with the system. Listener is clara.terminal:listener, the first application and the one that is launched when the window manager starts; Editor and Files are the subject of the next chapter.

What the list has under its line are commands: a name and a function of no arguments, which is called in a thread of its own when the name is picked, and which opens no window that anything waits for.

"Collect"

Starting in it

A world that is saved while the window manager runs starts in it: the screen goes from the boot report straight to the windows.

> (clara:save-image)
"/clara/clara.image"

("Listener" "Editor" "Files" "Hello")

What is defined comes back, the applications among it. The windows that were open do not: a window is pixels and a thread, and an image has neither, so the window manager starts with one Listener, as it does the first time. clara.windows:stop ends the applications and gives the screen back to the console, cleared; a world that is saved after that starts at the console again.

A window is the size it was opened with. Alt and Tab is the one key that is the window manager's own: nothing on the keyboard opens the list of applications, moves a window or closes one, which the pointer does, and the pointer has one shape.

Two applications come with the system besides the Listener: an editor for text, and a browser for the files of the disk. Each is a file of Lisp among the system's own, editor.lisp and files.lisp, which the system does not load as it starts. The file is loaded the first time its application is picked from Applications, or launched from a prompt, and the application can be unloaded again while everything else goes on.

The editor

Editor in the list opens a window with no text in it yet. From a prompt, the editor is launched with the name of a file, and the window has the file's name for its title:

> (find-package "CLARA.EDITOR")
NIL
> (clara.windows:launch "Editor" "/hello.lisp")
#<THREAD "Editor">
> (list (package-name (find-package "CLARA.EDITOR"))
        (clara.windows:window-title (clara.windows:focused-window)))
("CLARA.EDITOR" "/hello.lisp")

After the name, :columns and :rows say how large the text's part of the window is, in characters, and :x and :y where the window goes: (clara.windows:launch "Editor" "/hello.lisp" :columns 60 :rows 20). Without them it is 80 by 24, or what the screen has room for.

The window shows the text, with a bar under the place where what is typed goes in, and below the text a row that says which file this is, whether the text has changed since it was read or saved, and the line and the column of the cursor. That row is also where the editor says what it did, and where it asks for the name of a file.

A charactergoes in at the cursor.
Enterbegins a new line, as far in as the line it comes from.
Backspace, Deletetake out the character before the cursor, and the one at it. At the start and at the end of a line they join two lines.
Tabspaces, up to the next column that is a multiple of eight.
The arrowsmove the cursor by a character and by a line.
Home, Endthe start and the end of the line.
Page Up, Page Downa window's worth of lines up or down.
A clickputs the cursor where the pointer is.
Ctrl-Ssaves the text in its file. A text that has no file yet is asked for a name.
Ctrl-Oasks for the name of another file, and the text becomes that of the file.
Ctrl-Kcuts from the cursor to the end of the line, and at the end of a line the end itself. Typed several times in a row, it cuts as many lines.
Ctrl-Yputs back what Ctrl-K cut last, at the cursor, as often as it is typed.
Ctrl-Eevaluates the text, form by form, as load would: what it defines is defined, in every window. The row says how many forms there were, or what went wrong and in which line, where the cursor goes. Ctrl-C stops forms that do not end.
Ctrl-Q, the x in the titleclose the window.

While the row asks for a name, what is typed is the name: Enter hands it over, Backspace takes a character of it back, and Escape gives the question up. A name is a whole one, from the top of the volume, like /clara/notes.txt. A file that is not there yet is a new one, which the first Ctrl-S makes.

A text that has changed is not thrown away at the first asking. Ctrl-O, Ctrl-Q and the x say that the text is not saved, and do what they were asked when the same key comes again right after.

What to know about the editor as it is now:

  • A file is its lines. It is saved with a new line after each, so a file that did not end in one has one afterwards. The line with nothing in it after the last is where the text ends.
  • A character that the screen's font does not have shows as a box, a tab among them, and is kept as it is.
  • There is no undo, nothing is searched for, and nothing can be marked: Ctrl-K and Ctrl-Y are how text is moved.
  • What the forms of Ctrl-E print goes to the console, which is the serial port while the windows are on the screen. They are read in the package COMMON-LISP-USER unless the text says in-package.
  • Each editor window is a thread of its own with its own text. Two that have the same file open know nothing of each other.

Files

Files in the list opens a window on the top of the volume. From a prompt it can be told where to begin:

> (clara.windows:launch "Files" "/clara/")
#<THREAD "Files">
> (clara.windows:window-title (clara.windows:focused-window))
"Files in /clara/"

:columns, :rows, :x and :y after the name do for this window what they do for the editor's; it is 48 by 16 without them.

The window lists what the directory holds: the directories first, each with a slash at its end, then the files, and above them all ../, the way to the directory that this one is in. One name is picked, and shows the other way round.

The arrows up and down, Page Up, Page Down, Home, Endpick another name.
Entergoes into the directory that is picked, or opens the file that is picked in a new window of the editor.
Backspace, the arrow to the leftgo to the directory that this one is in.
A clickpicks the name it is on, and on the name that is picked does what Enter does.
Deleteasks whether the file that is picked is to be deleted, and y deletes it. Any other key does not.
Ctrl-Rreads the directory again: the window does not notice by itself what was written since.
Ctrl-Q, the x in the titleclose the window.

Every file opens in the editor, also one that is no text, which the editor says it cannot read. Directories are not made or deleted here, which two functions do at a prompt, and the window shows names and no sizes or dates.

  • clara.windows:remove-application does the same and takes the name out of the list. It is also what takes out an application that was defined at a prompt, like Hello.
  • What is typed at a prompt to define an application or to install one is written down with everything else that you define, so the launcher of a world that is made again, after an upgrade for one, has it in its list. clara.windows:remove-application and clara.windows:remove-command, typed at a prompt with the name written out, take the form that put it there out of /home/defined.lisp again.

  • The editor and the browser are unloaded and launched again the same way, and the system's editor.lisp can be changed in the editor: (clara.system:system-file "editor.lisp") is its name. A file that is installed by a name without a directory, as those two are, is one of the system's own.
  • What an application is installed as is part of the world, and is saved with it. Whether its file has been loaded is too: a world that is saved after the editor was used starts with the editor in it.

The package CLARA.UNSAFE

For drivers. What can be read with one of the first seven can be written with setf. The eight after give-screen are the compiler's and the translator's. The first two are a function made of code, and the code of a function: code is looked at before it is made a function, and refused when it points where it should not; that it uses its stack as it says is taken on trust, which is why the two are here. The other six are for the processor's own instructions: where the kernel keeps what they read, the instructions of a function handed to the kernel, how many bytes of them a function has, whether the processor runs a function, what the compiler made of every function that the processor does not run yet, and every function that has such instructions entered by them from then on. Those instructions are run as they are given, and nothing looks at them first. power-off and reset turn the machine off and start it again there and then, with nothing saved and nobody asked, which is what shutting down sees to before it calls them; power-button says whether the machine's power button has been pressed since it was last asked. sha-512 is the sum of some bytes of memory, by which a system's files are known to be what its list says, and start-state is what the kernel knows of this start and of the ones before it. The seven from digest to ecdsa are the arithmetic of HTTPS, on bytes of memory: a sum of them, SHA-256, SHA-384 or SHA-512; such a sum with a key; bytes closed with a key and opened again, with a tag that says nobody changed them; what two sides agree on who tell each other half of it; a number to a power, modulo another, which is what checking a signature of RSA's is; and whether two numbers are the signature that a key on a curve gives a sum.
